# JavaDoc 注释专家

## 核心原则

- 只补充或修正注释，**不改方法签名、泛型、返回值、实现逻辑**。
- 不重排 import，不格式化全文件，不改无关注解顺序。
- 保持当前文件及同包的注释风格一致。
- 先确认注释是否准确反映当前实现，发现明显错注释要修正。

## 优先补充范围（按优先级排序）

1. 公共 API、接口方法、record 参数、构造器
2. DTO / VO / Entity 字段（尤其导入导出、翻译、权限相关字段）
3. Mapper 默认方法、Service / Controller 公开方法
4. 公共模块里的私有辅助方法（涉及映射、批量处理、状态复制、降级语义）

## 注释风格规范

- 描述"做什么"和关键参数语义，不复述每行实现
- `@param` 名称必须和方法签名一致
- `void` 方法不写 `@return`
- 布尔返回值说明 `true` / `false` 含义
- 简单框架覆写方法可不重复注释；当前文件已有统一风格时保持一致
- 修正错注释时尽量保持最小 diff

### 格式模板

```java
/**
 * 一句话描述方法/类/字段的作用。
 *
 * <p>必要时补充详细说明（可选）。
 *
 * @param name 参数语义说明
 * @param ids  ID 集合，用于批量查询
 * @return 返回值的语义说明；布尔值说明 true/false 含义
 * @throws IllegalArgumentException 当参数非法时的说明
 */
```

### 字段注释

```java
/** 用户名，登录凭证，最长 64 字符 */
private String username;
```

## 常见错注释识别与修正

| 错误类型 | 示例 | 修正方向 |
|---------|------|---------|
| 描述与实际不符 | 方法查全部数据，注释写"根据用户查询" | 按实际实现重写描述 |
| @return 笼统 | 返回树/映射/分页，只写"结果" | 写明具体返回结构和语义 |
| 参数类型变了注释没改 | 参数从 `String` 变成 `Collection`，注释还写"ID 串" | 按新参数类型重写 |
| @param 名称不匹配 | 签名是 `userId`，注释写 `uid` | 对齐签名中的实际参数名 |

## 方法内部注释规范

梳理方法体内部实现逻辑，在关键位置添加行内注释，帮助维护者快速理解"为什么这么做"。

### 什么时候加

- 复杂业务逻辑、条件分支（尤其含多个 `if/else`、`switch` 嵌套）
- 非直觉算法或性能优化手段（位运算、特殊排序策略、批量分片等）
- 业务规则映射（状态码转换、枚举映射、降级策略）
- 循环中隐含的业务语义（累计、过滤、分组、去重）
- 异常捕获中的补偿或兜底逻辑
- 跨服务调用、重试、超时处理的意图说明
- 与外部系统交互时的特殊处理（序列化兼容、协议适配）

### 什么时候不加

- 自解释代码：`getter` / `setter`、简单赋值、标准 CRUD
- 变量名已足够清晰的操作（`userList.add(user)` 不需要注释）
- 框架样板代码（注解配置、Bean 注册）
- 每行代码后面都加——这是反模式

### 注释位置与风格

- 放在逻辑块**之前**，而不是每行后面
- 用 `//` 单行注释，不用 `/* */` 块注释（块注释留给 JavaDoc）
- 说"为什么"而不是翻译代码：`// 超时降级：返回缓存数据避免阻塞主流程` 而非 `// catch TimeoutException`
- 保持当前文件已有的注释缩进和空行风格

### 示例

```java
public List<OrderVO> queryOrders(QueryParam param) {
    // 先走缓存，命中则直接返回，避免重复查库
    List<OrderVO> cached = orderCache.get(param.getKey());
    if (cached != null) {
        return cached;
    }

    // 分页查询数据库，按创建时间倒序
    List<Order> orders = orderMapper.selectByParam(param);

    // 转换为 VO 并填充关联的用户信息
    List<OrderVO> result = orders.stream()
            .map(this::toVO)
            .collect(Collectors.toList());

    // 批量查询用户名，避免 N+1 问题
    fillUserNames(result);

    // 写回缓存，TTL 5 分钟
    orderCache.put(param.getKey(), result, Duration.ofMinutes(5));
    return result;
}
```

### 常见内部注释问题

| 问题 | 示例 | 修正方向 |
|------|------|---------|
| 翻译代码而非解释意图 | `// 遍历 list` 跟在 `for` 循环后 | 改为说明循环的业务目的 |
| 过时注释 | 代码已改为批量查询，注释还写"逐条查询" | 按实际实现重写 |
| 注释位置不对 | 注释在 `return` 后面 | 移到逻辑块之前 |
| 注释过多 | 每行都有注释，噪音大于信息 | 删除自解释行的注释 |

## 已有注释合规审查

当目标文件/目录已存在 Java 变量注释或方法注释时，**必须先审查再决定补充还是修正**，不可跳过已有注释直接新增。

### 审查流程

1. **逐条扫描**：遍历目标范围内所有已有的 `/** */` JavaDoc 和 `//` 行内注释
2. **逐项比对**：按下方检查清单逐条判定是否合规
3. **分类处理**：
   - 合规 → 保留不动
   - 不合规 → 原地修正，保持最小 diff
   - 缺失 → 按规范补充

### JavaDoc 注释检查清单

| 检查项 | 判定标准 | 不合格示例 |
|--------|---------|-----------|
| **描述准确性** | 注释描述与代码实际行为一致 | 注释写"查询单条"，实际返回 List |
| **@param 对齐** | 每个参数都有对应 `@param`，名称与签名完全一致 | 签名 `userId`，注释写 `@param uid` |
| **@return 完整性** | 非 void 方法必须有 `@return`，且描述具体语义 | `@return 结果` （过于笼统） |
| **void 无 @return** | void 方法不应有 `@return` 标签 | void 方法写了 `@return void` |
| **布尔值语义** | 返回 boolean 时说明 true/false 含义 | `@return 是否成功`（未说明何谓"成功"） |
| **@throws 匹配** | 声明的异常确实在方法体中抛出，未遗漏关键异常 | 声明了 `IOException` 但方法内无 IO 操作 |
| **过时信息** | 注释中提及的类名、方法名、参数类型与当前代码一致 | 注释引用已重构删除的旧方法名 |

### 变量 / 字段注释检查清单

| 检查项 | 判定标准 | 不合格示例 |
|--------|---------|-----------|
| **语义清晰** | 注释说明字段的业务含义，非简单重复字段名 | `/** 用户名 */ String username` 字段名已自解释，注释无增量信息 |
| **约束标注** | 长度、范围、枚举值、是否必填等约束已标注 | 数据库字段 `varchar(64)` 但注释未提及长度 |
| **与代码一致** | 注释描述与字段实际用途一致 | 注释写"创建时间"但字段实际存的是更新时间 |

### 行内注释检查清单

| 检查项 | 判定标准 |
|--------|---------|
| **解释意图** | 注释说"为什么"而非翻译代码 |
| **位置正确** | 注释在逻辑块之前，不在代码行尾（短注释除外） |
| **时效性** | 注释与当前实现一致，无过时描述 |
| **噪音控制** | 不存在对自解释代码的冗余注释 |

### 修正原则

- **最小 diff**：只改不合规的部分，不动合规的注释
- **保持风格**：修正后的注释与同文件其他注释风格一致
- **不猜意图**：如果无法从代码推断注释原意是否正确，保留原注释并标注 `// TODO: 待确认注释准确性`

## 执行流程

### 1. 分析阶段

- 读取目标文件，理解当前代码结构和已有注释风格
- 如果是目录，先列出所有 `.java` 文件，按优先级排序
- 识别哪些方法/类/字段缺少 JavaDoc 或注释有误
- 识别哪些方法体内部缺少逻辑注释或注释已过时

### 2. 审查阶段（已有注释必检）

- 遍历目标范围内**所有已有的 JavaDoc 和行内注释**
- 按「已有注释合规审查」章节的检查清单逐项比对
- 标记三类结果：✅ 合规保留 / ⚠️ 不合规待修正 / ❌ 缺失待补充
- 对不合规的注释，记录具体违反哪条规则

### 3. 补充与修正阶段

- 先修正审查中发现的不合规注释（最小 diff）
- 再按优先级补充缺失的 JavaDoc（方法/类/字段级别）
- 梳理方法内部实现逻辑，在关键位置补充行内注释
- 对于生成 Java 代码的场景：所有新增方法、类、字段必须在编写时同步附带 JavaDoc；方法体内复杂逻辑必须同步附带行内注释
- 保持与文件中已有注释的风格一致

### 4. 自检阶段

写入注释后执行以下检查：

- **实现一致性**：新增/修改的 JavaDoc 和行内注释是否和当前实现一致
- **参数对齐**：`@param` 名称是否和方法签名完全一致
- **行内注释质量**：是否说"为什么"而非翻译代码；是否放在逻辑块之前
- **噪音检查**：是否对自解释代码加了多余注释
- **最小变更**：如果存在 Git，运行 `git diff --check` 确认只改了注释或文档
- **无遗漏**：优先补充范围内的所有目标是否都已覆盖
